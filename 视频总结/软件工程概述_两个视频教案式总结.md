## 一、先看全课逻辑

这两个视频围绕一条主线展开：

> 软件规模越来越大、功能越来越复杂、用户越来越多，个人或小作坊式开发逐渐无法应对；因此必须把工程化的规范、流程、方法和管理思想引入软件开发，这就形成了软件工程。

第 1 部分主要回答：**为什么需要软件工程？**

第 2 部分主要回答：**软件工程具体怎样组织软件开发？**

全课逻辑可以概括为：

```text
软件的发展
    ↓
项目规模和复杂度增加
    ↓
出现软件危机
    ↓
引入工程化思想
    ↓
建立软件生命周期、开发方法和过程模型
```

## 二、第 1 部分：为什么需要软件工程

### 1. 课程定位和学习方式

开头的课件展示了课程性质和成绩构成：

- 软件工程是专业核心必修考试课；
- 考试成绩占 50%，平时成绩占 50%；
- 平时成绩包括出勤、课堂表现和实验报告；
- 前期以理论学习为主，后期安排实验课；
- 学习方式是“课上学习、课下复习、实验课练习”。

教师强调，不要只把教材当成需要死记的文字，而要先理解整门课的知识结构。教材是辅助材料，课堂会按照更容易理解的逻辑重新组织内容。

### 2. 学习软件工程有什么用

软件工程的学习意义主要有以下几方面：

1. 建立软件开发的全局视角，理解编程语言、数据库、操作系统、计算机网络等课程在完整开发过程中的位置。
2. 为开发、测试、运维、实施、产品经理、解决方案工程师等软件行业岗位打基础。
3. 为考研复试以及软件相关资格考试提供基础。
4. 帮助理解毕业设计和毕业论文的结构。
5. 最基本的作用是帮助学生掌握课程内容、顺利完成学业。

这里的关键观点是：**软件行业不只有写代码这一种工作。**

### 3. 什么是软件

视频先后展示了教材、英文教材和课件中的多个定义，最后归纳为：

> **软件 = 计算机程序 + 数据 + 文档**

其中：

- **程序**：描述计算机要完成什么任务，以及按照什么规则完成任务；
- **数据**：软件运行过程中使用、产生和保存的信息；
- **文档**：说明需求、设计、使用、维护和运行方式的资料。

因此，一个网站或手机 App 不只是代码，还包括数据库、图片、配置文件、说明资料以及运行它所需要的环境。

### 4. 课件中的服务器关系图

第 1 部分的重要画面是一张“终端—服务器—程序—数据”的关系图。图中包含手机、电脑等终端，服务器、操作系统、应用服务器、应用程序、文件系统和数据库。

以访问教务系统为例，过程是：

1. 用户在浏览器中输入域名；
2. DNS 将域名解析为 IP 地址；
3. 终端根据 IP 地址向服务器发起请求；
4. 服务器上的操作系统和应用服务器运行应用程序；
5. 程序从数据库和文件系统中读取用户需要的数据；
6. 服务器将处理结果返回给浏览器，这就是响应。

这个图说明了为什么软件不能简单理解为“几段代码”：真正的软件是程序、数据、文件和运行环境共同协作形成的系统。

### 5. 软件的六项基本特性

课件列出了完整软件应具备的六项特性：

| 特性 | 初学者理解 | 例子 |
| --- | --- | --- |
| 功能性 | 能完成预定任务 | 打车、购物、办公或娱乐 |
| 可靠性 | 出错时能够容错、容灾 | 服务器故障后仍能提供服务 |
| 可用性 | 容易学习和操作 | 用户能够快速学会使用 |
| 效率性 | 节省时间和资源 | 医院挂号从半小时缩短到几分钟 |
| 可维护性 | 后期容易修复和扩展 | 能够加补丁、改功能 |
| 可移植性 | 能迁移到其他环境 | 迁移到新服务器后仍能运行 |

教师特别用云计算中的数据迁移说明可移植性和可靠性：大型业务在机房维护或服务器迁移时，最好让用户几乎感觉不到服务中断。

### 6. 软件的发展趋势

视频用软件和编程语言的发展说明，软件经历了从简单到复杂、从个人开发到团队协作的发展过程：

- 早期主要使用机器语言；
- 后来出现汇编语言和更容易理解的高级语言；
- 随后出现操作系统和图形化界面；
- 最终发展出大量复杂的操作系统、办公软件、互联网产品和大型应用。

需要记住的不是每一个年份，而是这条趋势：

> 软件从个人开发、小作坊开发，逐渐发展为大型团队和公司协同开发。

软件通常分为两类：

- **系统软件**：Windows、Linux、macOS 等操作系统；
- **应用软件**：Word、播放器、微信、游戏等面向具体应用的软件。

### 7. 什么是工程

课件中的定义是：

> 工程是综合运用科学理论和技术手段，为实现某个目标而进行的系统性活动。

教师用修桥来解释。修桥不能“今天有空砌两块砖，明天再继续”，而要经历设计、预算、施工、验收和维护等环节。

因此，工程的重点不只是事情复杂，而是：

> 为了完成一个大型目标，按照规范、流程和方法，组织多人协同完成。

软件开发也一样。除了编码，还要进行需求分析、设计、测试、发布和维护。

### 8. 软件危机

课件展示了“软件危机 Software Crisis”和相关历史资料。视频指出，1968 年北大西洋公约组织相关会议正式提出了“软件危机”这一概念。

软件危机是指大型软件开发和维护过程中出现的一系列严重问题，例如：

- 开发进度无法预测；
- 开发成本难以控制；
- 最终功能不能满足用户需求；
- 软件质量无法保证；
- 软件后期难以维护；
- 缺少必要的文档资料。

视频列举了三个案例：

1. 丹佛国际机场项目投入巨大，却无法按照计划启用；
2. IBM OS/360 操作系统存在大量 Bug；
3. 美国银行信托软件项目延期多年，成本大幅超出预算，最后被迫放弃。

这些案例的共同问题是：项目规模已经很大，但开发方式仍然像个人或小作坊一样随意，缺少统一的需求、设计、协作、测试和管理机制。

所以，软件危机推动了软件工程的产生。

### 9. 第 1 部分的阶段性结论

> 编程语言解决的是“代码怎么写”；
>
> 软件工程解决的是“怎样把一个大型软件成功做出来”。

## 三、第 2 部分：软件工程怎样组织开发

### 1. 软件工程的定义

视频介绍了多个定义，并将其翻译成初学者容易理解的话：

> 软件工程就是按照一套规范的方法和流程，经济、高质量地开发、运行和维护可靠的软件。

IEEE 的定义强调三点：

- 使用系统化、严格约束、可量化的方法；
- 这些方法应用于软件的开发、运行和维护；
- 同时研究这些方法本身。

软件工程是一门交叉学科，涉及计算机科学、数学、工程科学和管理科学：

- 计算机科学和数学用于建立模型、算法和程序；
- 工程科学用于制定规范、设计系统和评估成本；
- 管理科学用于管理计划、资源、质量和成本。

### 2. 软件工程的三要素

课件用三个图标展示软件工程的三要素：

1. **方法**：按照什么思路分析、设计和开发软件；
2. **工具**：使用什么软件辅助设计、编码、测试和管理；
3. **过程**：怎样组织开发阶段、人员协作和工作交接。

软件工程的基本目标是：降低成本、提高质量、满足用户需求，并让软件能够可靠运行。

### 3. 软件生命周期

视频先用线程生命周期帮助理解“生命周期”：一个线程会经历启动、等待、运行、唤醒和消亡等阶段。

类似地，软件生命周期是：

> 软件从产生、开发、运行到最终维护或报废的全过程。

课件将软件生命周期分为三个时期、八个阶段：

| 时期 | 阶段 | 要解决的问题 |
| --- | --- | --- |
| 软件定义时期 | 问题定义 | 到底要开发什么软件 |
| 软件定义时期 | 可行性分析 | 这个项目能不能做、值不值得做 |
| 软件定义时期 | 需求分析 | 软件具体需要哪些功能 |
| 软件开发时期 | 总体设计 | 系统整体结构怎样搭建 |
| 软件开发时期 | 详细设计 | 各模块内部怎样实现 |
| 软件开发时期 | 编码和单元测试 | 编写程序并检验单个模块 |
| 软件开发时期 | 综合测试 | 检验整个系统是否符合要求 |
| 软件运行维护时期 | 软件维护 | 修复问题、升级功能、适应变化 |

每个阶段都有明确任务，并会形成相应文档，作为下一阶段的工作依据。例如，需求分析结果是系统设计的输入，系统设计结果又是编码实现的输入。

这说明软件开发不是“想到哪写到哪”，而是一条有输入、有处理、有输出的工作链。

### 4. 软件定义时期的三个阶段

#### 问题定义

先弄清楚客户到底想做什么。例如客户提出“开发一个人力资源管理系统”，开发方必须进一步确认系统的目标和范围。

#### 可行性分析

判断项目是否值得做、能不能做，包括：

- 技术上是否可行；
- 经济上是否划算；
- 法律和社会层面是否允许；
- 时间、人员和资源是否足够。

#### 需求分析

把模糊的目标进一步转化为具体的功能、模块、流程和约束。视频强调，需求分析通常是软件定义时期工作量最大的部分，因为程序员只有真正理解需求后才能正确编码。

### 5. 软件开发时期的三个阶段

软件开发不是一上来就写代码，而是：

1. 先进行总体设计，搭建系统整体结构；
2. 再进行详细设计，明确各模块的具体实现方式；
3. 然后编码、单元测试和综合测试。

这样做的目的，是把复杂系统拆成能够理解、协作和验证的部分。

### 6. 软件运行与维护时期

软件开发完成并不意味着工作结束。软件上线后还会遇到：

- 用户提出新增功能；
- 用户数量增加，需要扩容；
- 服务器和机房需要迁移；
- 运行过程中出现故障；
- 操作系统、数据库或网络环境发生变化。

这些工作属于运行与维护，也就是通常所说的运维。

视频还说明了公有云、私有云和混合云的区别：敏感数据往往保留在自己的私有环境中，而高并发、查询类业务可以借助公有云，实际项目中也可能把二者结合起来。

### 7. 软件开发方法

软件工程方法学可以简单理解为：

> 开发软件时采用的一整套思路、方法和套路。

视频重点讲了结构化方法和面向对象方法。

#### 结构化方法

核心记忆句：

> **自顶向下，逐层分解。**

它按照功能拆分系统。例如图书管理系统可以拆分为用户登录、图书借阅、图书归还、图书查询和图书管理，再继续拆分每个功能，直到不能再拆为止。

结构化方法关注的是：

> 系统有哪些功能，以及这些功能如何逐层分解。

#### 面向对象方法

面向对象不是“写了 class”这么简单，而是一种分析现实世界的思想。它关注：

- 系统中有哪些独立对象；
- 每个对象有什么属性和行为；
- 对象之间是什么关系；
- 对象如何相互协作。

教师用“大象装进冰箱”的例子说明：

- 面向过程：打开冰箱、放入大象、关上冰箱；
- 面向对象：分析“大象”和“冰箱”两个对象，让冰箱调用“装入大象”的方法。

面向对象的价值在于复用和扩展，包括封装、继承和多态等思想。图书管理系统中可以识别出学生、老师、图书、管理员和借阅记录等对象。

结构化方法和面向对象方法不是互相排斥的。实际开发中可以先按功能划分系统，再在具体模块内部使用面向对象思想进行设计。

### 8. 软件过程模型

方法回答“按照什么思路开发”；过程模型回答：

> 怎样具体组织整个开发过程。

视频重点介绍瀑布模型和快速原型模型。

#### 瀑布模型

课件中的流程是：

```text
需求分析 → 系统设计 → 系统实现 → 系统测试 → 运行与维护
```

核心特点：

> 每个阶段严格按照顺序进行，前一阶段结束后才能进入下一阶段。

上一阶段的成果，是下一阶段的输入。例如需求分析的结果交给系统设计，系统设计的结果交给系统实现。

优点：

- 思路清晰；
- 每个人知道当前阶段的任务；
- 每个阶段都有文档；
- 便于制定计划和管理；
- 适合需求稳定的项目。

缺点：

- 要求需求一开始就比较明确；
- 客户在中后期参与较少；
- 问题通常到后期才被发现；
- 需求变化时修改成本很高；
- 前期理解错误后，可能需要大范围返工。

适用场景包括需求相对稳定、规范要求严格的政务、军工、航天和部分银行系统。

#### 快速原型模型

快速原型模型适用于这样的情况：

> 用户知道自己想做什么，但说不清软件应该具体长什么样。

开发人员先制作一个可以点击、浏览和体验的原型，让客户确认界面布局、按钮位置和功能流程，然后再开发真正的软件。

必须注意：

> 原型不等于最终产品。

原型往往是静态或半静态页面，数据可能是写死的，并不一定具备完整的数据库、业务逻辑和性能能力。

优点：

- 帮助用户明确需求；
- 用户参与度和满意度较高；
- 修改原型的成本较低；
- 能够降低正式开发风险。

缺点：

- 用户可能误以为原型就是成品；
- 开发人员可能直接在不规范的原型代码上继续开发；
- 它解决的是需求不明确问题，不是开发效率问题。

视频画面展示了三种原型工具：**Axure、Figma、墨刀**。它们适合制作网页和 App 的界面原型，尤其适合重视 UI 和用户体验的互联网产品。

快速原型模型通常不是完整的软件生命周期模型，而是正式开发前用于获取和验证需求的一种策略。真实项目中，瀑布模型、快速原型模型以及其他模型可以根据阶段和场景组合使用。

## 四、两个视频合起来的知识框架

### 1. 基本概念关系

```text
软件：程序 + 数据 + 文档
工程：用规范、流程和协作完成目标
软件工程：用工程化方式开发、运行和维护软件
```

### 2. 三个重要层次

```text
软件工程
├── 方法：结构化、面向对象
├── 工具：开发、测试、原型和管理工具
└── 过程：生命周期和过程模型
```

### 3. 最重要的因果链

```text
软件规模扩大
    ↓
多人协作变多
    ↓
需求、沟通、质量和维护问题增加
    ↓
软件危机
    ↓
引入工程化思想
    ↓
生命周期 + 方法 + 工具 + 过程模型
```

## 五、初学者最容易混淆的概念

### 1. 程序不等于软件

程序只是软件的一部分。完整软件还包括数据、文件、文档和运行环境。

### 2. 写代码不等于完成软件开发

软件开发还包括需求、设计、测试、发布、运行和维护。

### 3. 面向对象不等于使用 class

class 是编程语言提供的语法工具；面向对象首先是一种按照对象、属性、行为和关系理解问题的思想。

### 4. 原型不等于产品

原型的目的主要是验证需求和交互方式，不代表已经完成真正的业务逻辑、数据处理和系统性能。

### 5. 测试通过不一定代表真正满足需求

测试通常只能说明程序符合已经写出的测试条件。如果最初的需求理解错了，程序即使通过测试，也可能不是客户真正需要的产品。

### 6. 结构化和面向对象不是非此即彼

两种方法可以结合使用。关键不是选择唯一正确的方法，而是根据项目阶段、对象和问题特点选择合适的组织方式。

## 六、最终总结

这两个视频最核心的结论是：

1. 软件不是单纯的代码，而是程序、数据和文档的组合。
2. 软件规模变大后，个人式、随意式开发会导致软件危机。
3. 软件工程的本质是用工程化方式组织软件开发。
4. 软件开发要经历需求、设计、编码、测试、运行和维护等阶段。
5. 方法、工具、过程是软件工程的三个基本要素。
6. 结构化方法按功能分解问题，面向对象方法按对象和关系理解问题。
7. 瀑布模型适合需求稳定的项目，快速原型模型适合需求或界面尚不明确的项目。
8. 实际开发中，各种方法和过程模型可以组合使用。

最适合记住的一句话是：

> **软件工程不是教你多写几行代码，而是教你如何把一个复杂的软件项目有组织、有质量、可维护地完成。**

## 七、自测题

1. 为什么程序能够运行，不代表软件一定满足用户需求？
   答：程序运行只能说明它基本能够执行，不代表功能正确、界面易用、性能可靠，也不代表它真正解决了用户的问题。若需求理解错误，即使测试通过，也可能不是用户需要的软件。

2. 软件为什么要包括数据和文档？
   答：数据是软件运行、处理和保存信息的基础；文档用于说明需求、设计、使用、运行和维护方法。没有数据和文档，软件难以使用、协作、维护和升级。

3. 软件危机产生的根本原因是什么？
   答：软件规模和复杂度不断增加、协作人员增多，但仍采用个人化、随意化的开发方式，缺少规范的方法、过程、测试和管理机制。

4. 软件工程的三个基本要素是什么？
   答：方法、工具、过程。方法解决如何分析和设计，工具提供开发和管理辅助，过程规定各阶段如何组织和协作。

5. 软件生命周期的三个时期分别是什么？
   答：软件定义时期、软件开发时期、软件运行维护时期。

6. 结构化方法的核心思想是什么？
   答：自顶向下、逐层分解。按照系统功能逐级拆分，直到形成可以实现和管理的基本模块。

7. 面向对象方法主要关注哪些内容？
   答：关注系统中有哪些对象、对象的属性和行为、对象之间的关系，以及对象之间如何相互协作。其重要思想包括封装、继承和多态。

8. 瀑布模型为什么要求需求明确？
   答：瀑布模型各阶段按顺序进行，前一阶段的成果是后一阶段的输入。需求一旦在前期确定，后期修改就会影响设计、编码和测试，返工成本很高。

9. 快速原型模型主要解决什么问题？
   答：主要解决用户需求不明确或难以表达的问题。通过制作可体验的原型，让用户提前确认界面、功能流程和交互方式。它不是为了单纯提高开发效率，也不等于最终产品。

10. 为什么实际项目中可以组合使用不同的方法和过程模型？
     答：方法和过程模型解决的是不同层面的问题，而且项目不同阶段、不同模块的特点也不同。例如，可以先用快速原型明确需求，再采用瀑布模型正式开发；系统整体按结构化方法分解，模块内部再使用面向对象方法设计。
